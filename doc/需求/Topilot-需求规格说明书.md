# Topilot 需求规格说明书

## 1. 文档目的
本文档用于定义 Topilot 项目“做什么”和“不做什么”，为后续架构设计、模块拆分、代码实现、测试和验收提供统一边界。本文档以当前代码实现为基线，需求描述应能够直接指导开发、测试与验收。

## 2. 项目背景

### 2.1 业务背景
现有通用 Agent 工具通常强调多工具、多插件和复杂编排，但对个人开发者与学生用户而言，更常见的问题是本机已有 GitHub Copilot CLI 能力，却缺少低成本、可远程、可延续上下文的移动端入口。Topilot 的目标不是重建独立模型平台，而是把用户已经登录好的本地 Copilot CLI 通过 Telegram Bot 暴露出来，使用户离开电脑后仍能在手机上继续会话、切换模型并接管本机运行中的 Copilot 会话。

### 2.2 核心问题
1. Copilot CLI 默认面向本地终端，移动端不可直接使用。
2. 用户在电脑端已启动的 Copilot 会话，离开电脑后难以继续查看过程和结果。
3. 现有通用 Agent 工具对个人场景存在依赖重、部署复杂、额外成本高的问题。
4. 个人用户需要最基本的安全边界，至少要限制可访问 Bot 的 Chat ID。

## 3. 项目目标
1. 将本地 Copilot CLI 能力桥接到 Telegram，形成可远程使用的个人 Copilot 助手。
2. 支持多会话管理、模型切换和本地运行中会话接管。
3. 在 Telegram 中展示流式回复、工具调用过程和会话历史摘要。
4. 保持项目轻量、可自托管、低依赖、低额外成本。

## 4. 目标用户与使用场景

### 4.1 目标用户
1. 已拥有 GitHub Copilot 账号并已在本机完成 CLI 登录的个人开发者或学生用户。
2. 需要在手机端远程查看和继续 Copilot 会话的单人使用者。
3. 希望复用本地开发环境，而不是额外接入独立云端大模型 API 的用户。

### 4.2 使用场景
1. 用户在常用电脑上保持 Copilot CLI 可用，离开电脑后通过 Telegram 向 Bot 发送需求，获取代码分析或回复结果。
2. 用户在电脑端已有运行中的 Copilot 会话，通过手机端 `/sessions` 找到会话并接管，继续查看工具调用过程和回复内容。
3. 用户需要针对不同任务保存多个上下文，通过新建会话和切换会话避免上下文污染。
4. 用户需要临时切换不同模型，比较响应风格和效果。

## 5. 项目范围

### 5.1 范围内功能
1. Telegram Bot 文本消息接收与命令处理。
2. Chat ID 白名单访问控制。
3. 本地 JSON 配置初始化、读取与覆盖写入。
4. 基于本地 Copilot CLI 的文本对话调用。
5. 基于 Copilot JSON 输出流的流式回复展示。
6. 工具调用、命令执行、目录检索等中间过程摘要化展示。
7. 每个 Chat 的会话创建、切换、删除、当前会话维护。
8. 扫描 `~/.copilot/session-state` 的本地会话发现、历史查看、接管和运行中轮询追踪。
9. 模型列表获取、回退、按钮切换和按 Chat 持久化保存。
10. 文件日志、控制台日志、基础故障提示。

### 5.2 范围外功能
1. 图片输入、图片生成、多模态对话。
2. 浏览器自动化和网页 UI。
3. 企业级多用户角色管理和细粒度权限体系。
4. 独立数据库、中间件、分布式调度与多实例高可用。
5. 插件市场、技能市场和远程命令审批工作流。

## 6. 功能需求总览

### 6.1 模块划分总览
Topilot 当前需求拆分为五个核心模块：
1. 配置与启动模块
2. Telegram 接入与访问控制模块
3. Copilot 对话与流式展示模块
4. 会话管理与接管模块
5. 模型发现与切换模块

## 7. 详细功能需求

### 7.1 配置与启动模块

#### 7.1.1 功能概述
该模块负责把“可运行”这件事落地，包括首次初始化、配置存储、配置校验和启动前诊断。

#### 7.1.2 结构化需求
1. 系统应支持首次运行自动触发交互式初始化。
2. 系统应支持执行 `topilot init` 手动初始化配置。
3. 系统应支持执行 `topilot doctor` 输出默认应用目录、配置路径、配置存在状态，以及基础配置健康信息。
4. 系统应把配置写入固定路径 `~/.topilot/config.json`，并在配置覆盖时生成带时间戳的备份文件。

### 7.2 Telegram 接入与访问控制模块

#### 7.2.1 功能概述
该模块负责接收 Telegram 消息，暴露命令入口，并对除 `/whoami` 外的业务能力执行白名单控制。

#### 7.2.2 结构化需求
1. 系统应支持接收文本消息并把非命令文本视为 Copilot 对话输入。
2. 系统应支持以下命令：`/start`、`/whoami`、`/session_current`、`/sessions`、`/session_new`、`/session_use`、`/model`、`/status`。
3. 系统应基于 `telegram.allowed_chat_ids` 执行授权校验；当白名单为空时，默认允许所有 Chat 访问。
4. 对未授权的 Chat，系统应拒绝调用，并返回如何获取 `chat_id` 的提示信息。
5. `/whoami` 必须保持可用，用于协助获取授权所需的 `chat_id`。
6. `/status` 应展示后端状态，以及当前会话、来源、状态、模型和工作区摘要，并提供后端诊断按钮以查看命令、解析路径、工作区、模型、调用参数、候选模型和待处理问题。
7. 系统启动时应向 Telegram 注册公开命令菜单；`/start`、`/status`、`/model`、`/sessions` 和 `/session_current` 等入口应提供内联按钮，降低移动端输入成本。

### 7.3 Copilot 对话与流式展示模块

#### 7.3.1 功能概述
该模块负责把 Telegram 文本请求转换为本地 Copilot CLI 调用，并把 CLI 的 JSON 流式输出转成适合手机端阅读的过程日志和最终回复。

#### 7.3.2 结构化需求
1. 系统应使用当前会话 ID 调用 Copilot CLI，确保上下文连续性。
2. 系统应支持为每个 Chat 保存当前模型并在调用时生效。
3. 系统应支持配置超时时间、推理强度、是否自动附带工作区目录、是否允许全部工具。
4. 系统应把 `assistant.message_delta` 实时刷新到 Telegram 回复消息中。
5. 系统应把 `tool.execution_start`、`tool.execution_complete` 等事件转为中文摘要日志。
6. 系统应过滤 `session.tools_updated`、`subagent.completed` 等低价值噪声事件。
7. 当 Copilot CLI 失败、超时、返回空结果或未就绪时，系统应给出明确失败提示。

### 7.4 会话管理与接管模块

#### 7.4.1 功能概述
该模块负责维护每个 Chat 的当前会话、会话列表、本机会话接管与历史追踪，是项目区别于普通 Bot 问答器的核心能力。

#### 7.4.2 结构化需求
1. 每个 Chat 应维护独立的当前激活会话。
2. 当 Chat 首次发起请求且无可用会话时，系统应自动创建默认会话。
3. 系统应支持手动新建会话并切换。
4. 系统应支持按会话 ID 前缀切换已有会话。
5. 系统应扫描 `~/.copilot/session-state`，识别本地会话的工作区、模型、运行状态、最后事件时间和最近历史。
6. 系统应支持将本地发现的会话接管到当前 Telegram Chat。
7. 对运行中的会话，系统应支持在会话详情页接管后轮询历史并持续刷新同一条消息，直到会话稳定结束。
8. 系统应支持删除 Bot 侧会话记录，并尝试同步删除对应本地会话目录。

### 7.5 模型发现与切换模块

#### 7.5.1 功能概述
该模块负责在启动时发现当前 Copilot CLI 可用模型，并通过 Telegram 内联按钮为用户提供可切换入口。

#### 7.5.2 结构化需求
1. 系统应在启动时优先执行 `copilot --help`，只从 `--model` 参数块解析可用模型列表；若主帮助未列出模型，应继续从 `copilot help config` 的 `model` 配置段解析候选模型。
2. 当实时解析失败时，系统应回退到配置文件中的 `copilot.available_models` 列表。
3. `/model` 应展示当前模型和候选模型按钮。
4. 用户点击模型按钮后，系统应校验模型合法性，并把模型选择持久化到当前 Chat。

## 8. 非功能需求

### 8.1 性能
1. Bot 对用户请求的处理必须支持流式输出，而不是仅返回最终结果。
2. 单条 Telegram 文本展示必须控制在安全阈值内，项目以 3500 字符作为分块或截断阈值。
3. 运行中会话自动追踪的轮询间隔默认 2 秒；运行时按 1 至 15 秒范围生效，超出范围的配置按边界值处理。

### 8.2 稳定性
1. 配置文件不存在、为空或 JSON 非法时，系统必须明确报错，不能静默失败。
2. Copilot CLI 返回非零退出码、超时、空输出时，系统必须给出清晰错误信息。
3. 过程消息和回复消息必须具备去重与限频机制，避免 Telegram 高频编辑报错。

### 8.3 安全性
1. 系统必须提供 Chat 白名单控制能力。
2. 敏感配置必须存储在外部配置文件，禁止写入源码。
3. 项目当前只承诺个人可信环境下的基础安全，不承诺企业级隔离和审计。

### 8.4 可维护性
1. 核心代码必须按配置、Bot 接入、任务编排、会话扫描、持久化等维度拆分。
2. 配置项、命令、数据结构和阶段计划必须同步维护文档。
3. 文档和代码的命名、目录、功能边界必须一一对应。

## 9. 数据需求
1. 配置数据保存在 `~/.topilot/config.json`。
2. 对话历史保存在 `~/.topilot/data/chats.json`。
3. 会话与模型状态保存在 `~/.topilot/data/sessions.json`。
4. 本地 Copilot 会话扫描数据来源于 `~/.copilot/session-state/`。
5. 日志写入 `~/.topilot/logs/app.log`。

## 10. 最终交付目标
1. 交付一个可通过 `topilot start` 启动的 Telegram Bot。
2. 已授权用户能够通过 Telegram 发起文本对话、切换模型、管理会话、接管本机会话。
3. 仓库中提交完整 Markdown 文档，覆盖需求、架构、计划、设计、测试、验收和根目录规范文件。
4. 文档与代码保持一致，教师仅通过 Git 仓库即可完成验收。

## 11. 成功标准
1. 授权 Chat 能完成从发送文本到收到 Copilot 回复的完整闭环。
2. `/sessions` 能展示会话列表，且可在会话详情页接管本地运行中会话。
3. `/model` 能展示候选模型并切换当前模型。
4. 配置初始化、日志写入和错误提示链路完整可用。
5. 课程验收要求的文档命名、目录和内容满足规范，且与代码实现一致。
