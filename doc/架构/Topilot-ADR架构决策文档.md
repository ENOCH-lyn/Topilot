# Topilot ADR 架构决策文档

## 1. 文档目的
本文档记录 Topilot 的关键架构决策及其依据，重点回答“为什么这样设计”。所有决策均以当前实现与目标运行形态为依据。

## 2. 总体架构概览

```text
Telegram 用户 / Feishu 用户
        ↓
telegram_bot.py / feishu_bot.py
        ↓
     task_runner.py
        ↓
       agent.py
        ↓
   本地 Copilot CLI

并行支撑模块：
- config.py / paths.py：配置与目录
- conversation_store.py：聊天历史
- session_store.py：会话与模型状态
- copilot_sessions.py：本地 session-state 扫描与接管
- logging_setup.py：日志
```

## 3. ADR-001：采用 Telegram + Feishu 作为远程交互入口

### 3.1 决策背景
项目的核心诉求是“离开电脑后继续使用本地 Copilot”，因此需要一个已普及、移动端体验成熟、接入成本低的远程交互渠道。

### 3.2 候选方案
1. 自研 Web 前端 + 后端接口
2. 桌面远程控制方案
3. Telegram Bot
4. Feishu Bot

### 3.3 决策结果
选择 Telegram Bot 作为主交互入口，并补充 Feishu Bot 作为并行平台入口，其中普通对话使用文本消息，快捷操作使用菜单和卡片。

### 3.4 选择原因
1. Telegram 天然具备移动端可用性和消息推送能力，适合完成命令、按钮和会话管理主流程。
2. Feishu 适合在国内办公或校园环境中接入现有聊天体系，长连接事件模式与本项目本地常驻运行形态匹配，且菜单与卡片能够承载状态、模型和会话快捷操作。
3. `python-telegram-bot` 与 `lark-oapi` 都能快速完成消息入口接入，不需要额外开发前端页面。

### 3.5 优缺点
优点：
1. 实现快，移动端体验成熟。
2. 指令、按钮和消息流可以直接覆盖当前需求。
3. 适合个人工具的轻量交互模式。

缺点：
1. 界面能力受聊天平台原生消息交互限制。
2. Telegram 与 Feishu 两套接入层需要分别维护。
3. 依赖对应平台网络可达性与账号配置状态。

## 4. ADR-002：采用本地 Copilot CLI 桥接，而不是直接接入模型 API

### 4.1 决策背景
项目目标是复用用户已有的 GitHub Copilot 能力，避免重新购买 API 或复制一套模型接入层。

### 4.2 候选方案
1. 直接接入 OpenAI / Azure OpenAI / 其他 LLM API
2. 通过本地 GitHub Copilot CLI 调用
3. 自建统一 Agent 服务后再让 Telegram 调用

### 4.3 决策结果
选择“本地 Copilot CLI 桥接”方案。

### 4.4 选择原因
1. 与项目目标一致，可直接复用现有 Copilot 账号能力。
2. 当前实现已通过 `--session-id <session_id>`、`--output-format json`、`--add-dir` 等参数完成 CLI 对接；当用户显式选择具体模型时才附带 `--model`，默认 `auto` 模式不传该参数。
3. 能直接利用 Copilot CLI 自带的工具调用和会话系统。

### 4.5 优缺点
优点：
1. 成本低，实施快。
2. 会话连续性天然依赖 Copilot CLI。
3. 可直接读取本机会话状态并实现接管。

缺点：
1. 运行环境受 Copilot CLI 安装与登录状态约束。
2. 解析模型列表依赖 CLI 帮助输出格式。
3. 未来若切换到底层模型供应商，重构成本较高。

## 5. ADR-003：采用单进程长轮询架构，而不是 Webhook 或多服务拆分

### 5.1 决策背景
项目规模小、使用者少，且重点在功能闭环而非高并发。

### 5.2 候选方案
1. Telegram Webhook + Web 服务
2. 单进程长轮询
3. Bot 接入层与任务执行层分离为多个进程

### 5.3 决策结果
选择“Telegram 长轮询 + Feishu 长连接后台线程”的单进程架构。

### 5.4 选择原因
1. `application.run_polling()` 足以满足 Telegram 个人场景。
2. Feishu 长连接不需要公网回调地址，适合本地常驻进程。
3. 单进程更易与本地 Copilot CLI 和文件存储协同。
4. Telegram 轮询层可在网络异常后由启动层重建 Application，不需要额外引入进程管理服务。

### 5.5 优缺点
优点：
1. 部署和调试简单。
2. 与本地 JSON 存储、会话扫描天然匹配。
3. 更适合当前单用户、自托管的运行场景。

缺点：
1. 不适合高并发和多实例扩展。
2. 可用性依赖单进程运行状态，适合配合本机守护脚本使用。

## 6. ADR-004：采用 JSON 文件存储，而不是数据库

### 6.1 决策背景
当前需要持久化的数据只有配置、聊天历史、会话列表和模型选择，规模较小。

### 6.2 候选方案
1. SQLite
2. MySQL / PostgreSQL
3. 本地 JSON 文件

### 6.3 决策结果
选择本地 JSON 文件。

### 6.4 选择原因
1. 数据结构简单，主要为按 Chat 维度的键值映射。
2. 不引入数据库可降低部署门槛。
3. JSON 便于直接检查与排错，也符合个人工具定位。

### 6.5 优缺点
优点：
1. 零额外基础设施。
2. 可读性强，便于直接检查。
3. 代码实现简单，与 `conversation_store.py`、`session_store.py` 相匹配。

缺点：
1. 并发写能力弱。
2. 不适合大规模数据和多实例共享。
3. 缺少事务和复杂查询能力。

## 7. ADR-005：通过扫描 `~/.copilot/session-state` 实现会话接管

### 7.1 决策背景
项目的差异化价值之一，是手机端能够继续查看电脑端已有的 Copilot 会话。

### 7.2 候选方案
1. 在 Topilot 内部自行维护一套独立会话系统
2. 读取 Copilot CLI 本地 `session-state` 目录并复用其会话元数据

### 7.3 决策结果
选择直接扫描 `~/.copilot/session-state`。

### 7.4 选择原因
1. 当前代码已实现对 `workspace.yaml`、`events.jsonl` 和 `inuse.*.lock` 的读取。
2. 能获取现有会话的工作区、模型、运行状态和历史摘要。
3. 不需要重复设计一套与 Copilot CLI 脱钩的会话协议。

### 7.5 优缺点
优点：
1. 能真正接管现有 Copilot 会话。
2. 与项目核心诉求高度一致。
3. 避免内部会话与外部会话分裂。

缺点：
1. 强依赖 Copilot CLI 的本地数据格式。
2. 若上游目录结构变化，需要及时适配。

## 8. ADR-006：将 CLI 流式 JSON 事件转译为“过程日志 + 最终回复”双通道展示

### 8.1 决策背景
终端中的大量原始事件直接搬到聊天平台会造成噪声过多、可读性差；不同平台的消息能力也不一致，需要统一业务语义并按平台特性分别渲染。

### 8.2 候选方案
1. 只发送最终答案
2. 原样转发所有 JSON 事件
3. 对事件分类：回复流进入回复消息，工具事件进入过程消息

### 8.3 决策结果
选择双通道展示。

### 8.4 选择原因
1. 既保留过程可见性，又避免用户被原始日志淹没。
2. 代码中已实现 `TelegramLiveProgress` 双消息模型、去重和限频，也已实现 Feishu 普通对话的文本分段发送与卡片快捷操作分流。
3. 更适合手机端阅读，并且便于跨 Telegram / Feishu 复用同一套事件转译结果。

### 8.5 优缺点
优点：
1. 可读性强。
2. 用户能看到执行过程和最终回答。
3. 有利于定位运行过程中的问题。

缺点：
1. 事件摘要规则需要维护。
2. 需要分别处理 Telegram 消息编辑频率、HTML 回退，以及 Feishu 文本分段和卡片刷新逻辑。

## 9. 模块拆分逻辑

### 9.1 模块边界
1. `cli/main.py`：CLI 命令入口，只负责初始化、启动和诊断。
2. `config.py` + `paths.py` + `logging_setup.py`：环境与基础设施。
3. `telegram_bot.py` + `feishu_bot.py`：平台接入层输入输出与交互组件。
4. `task_runner.py`：业务编排和模块协调中心。
5. `agent.py`：Copilot CLI 调用与流式事件解释器。
6. `conversation_store.py` + `session_store.py`：本地状态持久化。
7. `copilot_sessions.py`：外部会话扫描与接管。

### 9.2 开发顺序
串行依赖顺序如下：
1. 配置与路径
2. Bot 启动与基础命令
3. Copilot CLI 调用
4. 流式展示
5. 会话与模型持久化
6. 本机会话接管

并行性说明：
1. `conversation_store.py` 与 `session_store.py` 可并行开发。
2. `designer.md` 和交互文案设计可与 Telegram 菜单开发并行推进。

## 10. 架构约束与技术边界
1. 当前版本必须保持单实例单进程运行假设。
2. 当前版本必须保持本地文件存储，不引入数据库耦合。
3. 当前版本必须保持 Telegram 与 Feishu 作为聊天平台入口，不扩展为 Web UI。
4. 当前版本必须保持与 GitHub Copilot CLI 的本地桥接关系，而不是替换为其他模型 API。
5. 当前版本不以跨平台完美兼容为目标，Windows + PowerShell 是首要适配环境。
