## 4. 阶段拆分与依赖关系

### 4.1 阶段0：现状盘点与需求冻结
- 核心目标：彻底读懂现有代码，确认实际功能边界，剔除 README 草稿与代码不一致内容。
- 交付物：PRD、ADR、根目录规范文件初稿。
- 依赖关系：无前置依赖，是后续文档工作的入口。

### 4.2 阶段1：基础能力文档化与规范化
- 核心目标：把配置、启动、Telegram 接入、访问控制这些“系统可运行前提”写成可验收文档。
- 交付物：阶段1 执行计划、部署规范、交互规范。
- 依赖关系：依赖阶段0完成需求边界冻结。

### 4.3 阶段2：核心功能对齐与补文档
- 核心目标：把 Copilot 对话链路、流式展示、会话接管、模型切换转化为结构化执行计划和详细设计。
- 交付物：阶段2 执行计划、详细设计文档。
- 依赖关系：依赖阶段1完成基础入口与权限边界说明。

### 4.4 阶段3：测试与验收资料补齐
- 核心目标：建立功能验证矩阵，明确已实现、待补测、待补自动化测试的内容。
- 交付物：测试方案与测试用例、模块验收报告。
- 依赖关系：依赖阶段1、阶段2的模块计划和设计文档。

### 4.5 阶段4：提交前收口
- 核心目标：最终核对仓库目录、命名、索引、引用关系和教师可读性。
- 交付物：最终检查记录。
- 依赖关系：依赖前述全部文档完成。

## 5. 分阶段负责人说明
1. 项目负责人：负责需求边界确认、最终内容裁定、仓库提交与课程对接。
2. 文档整理：负责基于现有代码补齐文档、整理结构、统一术语、输出验收口径。
3. 若后续有组员加入，应按模块拆分负责人，不得跨模块无序修改文档。

## 6. 风险与应对

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 文档与代码不一致 | 直接影响课程验收 | 以 `src/topilot/` 实现为唯一事实来源，修改文档前先过代码 |
| 自动化测试覆盖仍偏基础 | 测试与验收材料说服力下降 | 已补齐基础 pytest 套件，并在测试文档和验收报告中明确未覆盖项 |
| Copilot CLI 环境依赖强 | 教师复现实验可能受阻 | 在 `cloud.md` 和测试文档中明确环境前置条件 |
| 旧版 `docs/` 草稿与 `doc/` 正式文档冲突 | 影响目录规范性 | 明确 `doc/` 为正式提交目录，`docs/` 仅历史参考 |

## 7. 量化交付标准
1. 所有课程正式文档均以 Markdown 形式提交到仓库。
2. 根目录强制文件命名必须准确：`agents.md`、`cloud.md`、`designer.md`。
3. `doc/` 目录必须包含“需求、架构、计划、设计、测试、验收”六类子目录。
4. 每个阶段计划文档必须具备输入、输出、实现逻辑、验收标准、测试方案、依赖关系六类内容。
5. 所有文档中出现的命令、配置项、路径、数据文件名必须能在代码或配置示例中找到对应实现。
