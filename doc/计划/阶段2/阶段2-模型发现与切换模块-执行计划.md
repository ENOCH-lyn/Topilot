# 阶段2-模型发现与切换模块-执行计划

## 1. 模块定位
模型发现与切换模块负责把底层 Copilot CLI 可用模型能力暴露给 Telegram 用户，并确保模型选择能够按 Chat 持久化保存，在后续对话中持续生效。

## 2. 模块核心功能
1. 启动时拉取可用模型列表。
2. 获取失败时回退到配置中的模型列表。
3. 在 Telegram 中以按钮形式展示模型切换入口。
4. 按 Chat 保存当前模型选择。

## 3. 输入与输出

### 3.1 输入
1. `copilot --help` 输出文本
2. 配置文件中的 `copilot.available_models`
3. Telegram `/model` 命令与模型按钮回调

### 3.2 输出
1. 运行期模型缓存列表
2. Telegram 模型选择键盘
3. `sessions.json` 中的 `models` 映射

## 4. 核心实现逻辑
1. `AssistantPlanner.fetch_available_models()` 优先解析 `copilot --help` 中 `--model <model>` 的候选值。
2. `TaskRunner.start()` 在应用启动后加载并缓存模型列表。
3. `/model` 命令使用 `_build_model_keyboard()` 构建两列内联按钮。
4. 模型回调先校验合法性，再调用 `SessionStore.set_model()` 持久化。

## 5. 技术方案与可选方案

### 5.1 选用方案
采用“运行时探测 + 配置回退”方案。

### 5.2 可选方案比较
1. 仅依赖手工配置模型列表：简单，但易过期。
2. 每次请求前都实时探测：准确但额外开销大。
3. 启动时探测并缓存，失败时回退配置：兼顾准确性和稳定性，最终选用。

## 6. 可自动化验收标准
1. 当 `copilot --help` 输出包含模型候选值时，系统启动后缓存的模型列表必须与解析结果一致。
2. 当实时获取失败时，系统必须回退到 `copilot.available_models` 配置，而不是返回空结果。
3. `/model` 返回的键盘必须采用两列布局，且当前模型按钮带 `✓` 标识。
4. 用户点击不存在于缓存列表中的模型时，系统必须拒绝切换并返回“模型不存在”提示。
5. 模型切换成功后，`sessions.json` 中当前 `chat_id` 的模型值必须更新，后续请求调用 Copilot CLI 时必须使用新模型。

## 7. 测试数据与测试方案

### 7.1 测试数据
1. 包含模型候选值的 `copilot --help` 输出样例。
2. 实时探测失败场景。
3. 配置回退模型列表样例。
4. 模型回调合法值与非法值样例。

### 7.2 测试方案
1. 对帮助输出解析逻辑做字符串级单元测试。
2. 对模型按钮布局做结构断言。
3. 对模型持久化与后续读取做状态断言。

## 8. 模块依赖关系
1. 依赖配置模块提供 CLI 命令和回退模型列表。
2. 依赖 Telegram 接入模块提供 `/model` 命令与按钮回调。
3. 依赖会话存储模块保存每个 Chat 的模型选择。

## 9. 开发顺序
1. 先完成模型帮助输出解析与回退逻辑。
2. 再完成 TaskRunner 级缓存。
3. 最后完成 Telegram 按钮展示与模型持久化。
