# 阶段2-模型发现与切换模块-执行计划

## 1. 模块定位
模型发现与切换模块负责把底层 Copilot CLI 可用模型能力暴露给 Telegram 与 Feishu 用户，并确保模型选择能够按 Chat 持久化保存，在后续请求中持续生效。

## 2. 模块核心功能
1. 启动时拉取可用模型列表。
2. 获取失败时优先回退到配置中的模型列表；配置列表为空时回退到当前默认模型。
3. 当默认模型为 `auto` 且未配置候选列表时，模型菜单只保留 `auto`，由 Copilot CLI 自行选择实际模型。
4. 在 Telegram 与 Feishu 中以按钮形式展示模型切换入口。
5. 按 Chat 保存当前模型选择。

## 3. 输入与输出

### 3.1 输入
1. `copilot --help` 输出文本
2. `copilot help config` 输出文本
3. 配置文件中的 `copilot.available_models`
4. Telegram `/model` 命令与模型按钮回调，以及 Feishu 模型卡片动作

### 3.2 输出
1. 运行期模型缓存列表
2. Telegram 模型选择键盘与 Feishu 模型切换卡片
3. `sessions.json` 中的 `models` 映射

## 4. 核心实现逻辑
1. `AssistantPlanner.fetch_available_models()` 优先解析 `copilot --help` 中 `--model <model>` 参数块内的候选值。
2. `_build_copilot_help_argv()` 复用正式 CLI 调用的入口兼容策略，普通命令直接追加 `--help`，Windows `.ps1` 入口通过 PowerShell `-File` 包装后追加 `--help`。
3. 若主帮助中的 `--model` 参数块未列出候选值，且默认模型不是 `auto`，则通过 `_build_copilot_config_help_argv()` 执行 `copilot help config`，从 `model` 配置段解析真实模型列表。
4. 解析帮助文本时只读取当前参数或配置段范围内的候选值，避免把 `--output-format` 的 `text/json` 等其他参数候选值误识别为模型。
5. `TaskRunner.start()` 在应用启动后加载并缓存模型列表。
6. `/model` 命令使用 `_build_model_keyboard()` 构建 Telegram 两列内联按钮；Feishu 侧使用模型卡片按钮展示当前模型和候选模型。
7. 模型回调或卡片动作先校验合法性，再调用 `SessionStore.set_model()` 持久化。
8. `_normalize_model_list()` 在展示和回调校验前去除空模型值与重复模型，保证按钮列表和合法性判断使用同一候选集合。

## 5. 技术方案与可选方案

### 5.1 选用方案
采用“运行时探测 + 配置回退”方案。

### 5.2 可选方案比较
1. 仅依赖手工配置模型列表：简单，但易过期。
2. 每次请求前都实时探测：准确但额外开销大。
3. 启动时探测并缓存，失败时回退配置：兼顾准确性和稳定性，最终选用。

## 6. 可自动化验收标准
1. 当 `copilot --help` 的 `--model` 参数块输出包含模型候选值时，系统启动后缓存的模型列表必须与解析结果一致。
2. 当主帮助未列出模型候选值、但 `copilot help config` 的 `model` 配置段包含模型列表时，系统必须从配置帮助中解析候选模型。
3. 当 `copilot --help` 中其他参数包含候选值时，系统不得把 `--output-format` 的 `text/json` 等非模型候选值加入模型列表。
4. 当 Copilot CLI 命令为 `.ps1` 时，帮助探测命令必须使用 PowerShell `-File` 方式执行，不能直接把 `.ps1` 当普通可执行文件调用。
5. 当实时获取失败时，系统必须回退到 `copilot.available_models` 配置；如果配置列表为空，必须至少回退到当前默认模型，而不是返回空结果。
6. 当当前模型为 `auto` 时，正式 Copilot CLI 调用必须省略 `--model`，不能向 CLI 传递 `--model auto`。
7. `/model` 返回的键盘必须采用两列布局，且当前模型按钮带 `✓` 标识。
8. 用户点击不存在于缓存列表中的模型时，系统必须拒绝切换并返回“模型不存在”提示。
9. 模型切换成功后，`sessions.json` 中当前 `chat_id` 的模型值必须更新，后续请求调用 Copilot CLI 时必须使用新模型。
10. 当模型缓存包含空值或重复值时，Telegram 模型菜单必须自动清理，最终按钮不得重复。
11. Feishu 模型卡片必须复用与 Telegram 一致的候选模型集合、合法性校验和持久化结果。

## 7. 测试数据与测试方案

### 7.1 测试数据
1. 包含模型候选值的 `copilot --help` 输出样例。
2. `--model` 无候选值、`--output-format` 包含 `text/json` 候选值的主帮助输出样例。
3. 包含 `model` 配置段的 `copilot help config` 输出样例。
4. 实时探测失败场景。
5. 配置回退模型列表样例。
6. 配置回退列表为空时的默认模型样例。
7. Windows `.ps1` 形式 Copilot CLI 命令样例。
8. 模型回调合法值与非法值样例。
9. 包含重复项和空值的模型列表样例。
10. `auto` 模型与过期模型持久化样例。

### 7.2 测试方案
1. 对主帮助和配置帮助输出解析逻辑做字符串级单元测试。
2. 对防止误读其他参数 choices 的回归场景做断言。
3. 对帮助命令组装逻辑做 `.ps1` 入口兼容性断言。
4. 对模型按钮布局做结构断言。
5. 对模型持久化与后续读取做状态断言。
6. 对模型列表清理、当前模型标识和 callback_data 做结构断言。

## 8. 模块依赖关系
1. 依赖配置模块提供 CLI 命令和回退模型列表。
2. 依赖 Telegram / Feishu 接入模块提供模型入口与按钮回调。
3. 依赖会话存储模块保存每个 Chat 的模型选择。

## 9. 开发顺序
1. 先完成模型帮助输出解析与回退逻辑。
2. 再完成 TaskRunner 级缓存。
3. 最后完成 Telegram / Feishu 按钮展示与模型持久化。
