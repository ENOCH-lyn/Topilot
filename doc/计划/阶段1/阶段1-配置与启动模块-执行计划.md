# 阶段1-配置与启动模块-执行计划

## 1. 模块定位
配置与启动模块是 Topilot 的运行入口，负责初始化应用目录、生成和读取配置、迁移旧版环境变量配置、诊断运行前状态，并最终启动 Telegram Bot。该模块直接决定项目是否能在目标主机上稳定起跑。

## 2. 模块核心功能
1. 构建 `~/.topilot/` 应用目录结构。
2. 提供首次运行交互式初始化。
3. 支持 `init`、`start`、`config-path`、`doctor`、`import-env` 等 CLI 命令。
4. 读取和校验 `config.json`。
5. 在配置覆盖时自动备份历史配置。

## 3. 输入与输出

### 3.1 输入
1. 用户在命令行输入的初始化参数。
2. 旧版 `.env` 文件内容。
3. `--home` 指定的自定义应用目录。

### 3.2 输出
1. `~/.topilot/config.json` 或自定义 home 下的配置文件。
2. `data/`、`logs/`、`workspace/` 等应用目录。
3. 标准输出中的诊断信息、错误信息和配置路径。

## 4. 核心实现逻辑
1. `paths.py` 使用 `build_app_paths()` 定义应用 home、数据、日志和工作区目录。
2. `config.py` 提供默认配置模板、JSON 读写、备份、旧版 `.env` 解析与迁移。
3. `cli/main.py` 负责解析 CLI 参数并调度初始化、诊断、迁移和启动流程。
4. `load_settings()` 在启动前对关键配置项执行强校验，至少保证 `telegram.bot_token` 存在。
5. `logging_setup.py` 在启动阶段配置文件日志和控制台日志。

## 5. 技术方案与选型说明

### 5.1 选用方案
采用“JSON 配置 + CLI 交互初始化 + 旧版 `.env` 迁移兼容”组合方案。

### 5.2 可选方案比较
1. 纯 `.env` 配置：简单，但层级结构表达弱，不利于扩展。
2. GUI 配置向导：体验更强，但超出当前项目复杂度。
3. JSON 配置：结构清晰、易扩展、便于备份和人工排查，最终选用。

## 6. 可自动化验收标准
1. 在空目录下执行 `topilot --home <临时目录> init --force`，完成交互后必须生成 `config.json`，且根节点包含 `telegram`、`copilot`、`runtime`、`storage`、`logging` 五个对象。
2. 当 `config.json` 已存在且内容发生变化时，再次写入必须生成 `config.backup-时间戳.json` 备份文件。
3. 执行 `topilot --home <临时目录> doctor` 时，输出中必须包含 `app_home=`、`config=`、`has_config=` 三行信息。
4. 当 `config.json` 缺少 `telegram.bot_token` 时，执行 `topilot --home <临时目录> start` 必须返回非零状态，并输出“配置项 telegram.bot_token 为空”或同等明确错误。
5. 对包含 `TELEGRAM_BOT_TOKEN`、`COPILOT_CLI_MODEL` 等字段的旧版 `.env` 文件执行 `topilot import-env` 后，生成的 JSON 配置字段必须与映射关系一致。

## 7. 测试数据与测试方案

### 7.1 测试数据
1. 正常 JSON 配置样例。
2. 缺少 Token 的异常配置样例。
3. 包含完整字段的旧版 `.env` 样例。
4. 覆盖写入前后的两份不同配置内容。

### 7.2 测试方案
1. 使用临时目录执行 CLI 集成测试，避免污染真实 `~/.topilot/`。
2. 通过文件存在性、JSON 字段校验和标准输出断言验证结果。
3. 对异常路径重点验证报错信息是否明确。

## 8. 模块依赖关系
1. 无业务前置模块依赖，是所有阶段开发的前提。
2. 为 Telegram 接入、日志、任务调度等模块提供运行配置。

## 9. 开发顺序
1. 先完成路径定义与目录创建。
2. 再完成默认配置模板和 JSON 读写。
3. 然后完成 CLI 命令入口。
4. 最后接入日志初始化和启动流程。
